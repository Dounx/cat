# Cat 事件中心

把各处来的事件接到一起，按规则判断，再触发动作。

```
QQ / 飞书 / 钉钉 / Discord / Telegram / GitHub / 企业微信 / 邮件 / RSS / 网页变动 / 接口变动 / 定时 / Webhook ──▶ 规则（条件、分支）──▶ 动作
                                                                                       ├─ 交给 AI（Claude Desktop / ChatGPT Desktop / DeepSeek Harness）
                                                                                       ├─ 原路回复、跨平台转发
                                                                                       └─ 发 HTTP 请求、跑脚本
```

- **插件化**：每个平台、每种 AI 都是独立进程的插件，用任何语言都能写。官方提供 Go 和 TypeScript SDK。
- **一键接入**：接入向导负责校验密钥、显示登录二维码、下载并配置依赖，配置表单由插件声明、界面自动生成。
- **从用途开始**：新建规则先选要做的事（聊天机器人、有变化就通知、定时让 AI 干活……），缺什么当场接入，规则自动搭好。
- **可调试**：规则不用保存就能拿收到过的事件试运行；收到的每个事件、规则对它做的每一步都有记录，历史事件可以重放。
- **两种形态**：桌面应用（托盘常驻）和无界面服务，共用同一个引擎和界面。

## 运行

需要 Go 1.24+、Node + pnpm（构建界面）、Bun（构建 TypeScript 插件）。

```bash
make run                                 # 构建界面、插件、桌面版 bin/cat-desktop 并启动
make run-web                             # 同上，但用无窗口的 bin/catd，然后打开 http://127.0.0.1:7788
```

桌面应用（macOS / Linux / Windows，在哪个系统上构建就打哪个系统的包，插件已打包在内）：

```bash
make app
```

| 系统 | 产物 | 构建前需要 |
| --- | --- | --- |
| macOS | `bin/Cat.app` | Xcode 命令行工具 |
| Linux | `bin/Cat-linux/`，有 `dpkg-deb` 时还有 `bin/cat_<版本>_<架构>.deb` | `libgtk-4-dev`、`libwebkitgtk-6.0-dev`（Ubuntu 24.04+ / Debian 13+） |
| Windows | `bin/Cat-windows/` | 在 Git Bash 里运行 `make`；运行时需要 WebView2（Windows 10/11 一般已自带） |

`Cat-linux` 和 `Cat-windows` 是免安装目录，放到哪里都能直接运行；Linux 下执行目录里的 `install.sh` 可以把 Cat 加进应用菜单。

`catd` 的主要参数：

| 参数 | 环境变量 | 说明 |
|---|---|---|
| `--addr` | `CAT_ADDR` | 监听地址，默认 `127.0.0.1:7788` |
| `--data` | `CAT_DATA` | 数据目录，默认 `~/.cat` |
| `--token` | `CAT_TOKEN` | 访问令牌。监听非本机地址时必须设置 |
| `--plugins` | `CAT_PLUGINS` | 额外的插件目录 |
| `--market` | `CAT_MARKET` | 插件市场索引地址；填 `off` 关闭（默认读取最新 Release 的 `index.json`） |

Cat 放在反向代理或内网穿透后面时，到「接入」页列表下面设置「对外地址」：Webhook 这类接入显示和复制的接收地址会以它开头，而不是以你打开界面的地址开头。它只改显示的地址，不改 Cat 监听在哪。

运行日志除了打到终端，也写进数据目录下的 `logs/cat.log`（默认 `~/.cat/logs/cat.log`），桌面版同样如此；插件输出的日志也在里面。文件超过 10 MB 会改名为 `cat.log.1` 并另起新文件，最多保留 3 个旧文件。程序崩溃（panic）时的堆栈写在同一目录的 `crash.log`；下次启动会把它改名为 `crash-<崩溃时间>.log` 留档，并在 `cat.log` 里提示一行。

## 第一条规则

界面只有三页：「规则」（什么时候、满足什么条件、做什么）、「接入」（把聊天软件、要盯的东西和 AI 接进来）、「记录」（收到了什么，规则对它做了什么）。

第一次打开时，「规则」页会问你想做什么。选一个，比如「收到 Webhook 就做点什么」：

1. 它会列出需要的东西。还没有 Webhook 就点「现在接入」，接好后点「下一步」，打开的画布上规则已经搭好：一个触发节点连着一个「HTTP 请求」动作。
2. 点动作节点，填上地址。请求体里可以用「插入变量」放进事件的内容，它在输入框里显示成一个标签。
3. 到「接入」页复制这个 Webhook 的地址，发一个请求：

   ```bash
   curl -X POST http://127.0.0.1:7788/ingress/<Webhook 地址里的那一段> -d '{"text":"please deploy"}'
   ```

4. 回到规则，点「试运行」：拿刚收到的事件把规则跑一遍，每个动作节点上会标出成功还是失败，点进去看结果。满意了再保存。
5. 之后每次请求的结果都在「记录」里。点开一条记录，在触发的规则上点「看流程」，可以在规则的图上看到这次走过的路径，点节点看它用了什么、得到什么。

其他几个起点：

| 起点 | 需要接入 | 生成的规则 |
| --- | --- | --- |
| 聊天机器人 | 一个聊天渠道、一个 AI | 有人 @ 机器人 → 交给 AI → 答案发回原处 |
| 有变化就通知我 | 一个监控（RSS、网页变动、接口变动）、一个聊天渠道 | 有变化 → 把内容发到你选的会话 |
| 定时让 AI 干活 | 定时触发、一个 AI、一个聊天渠道 | 到点 → 交给 AI → 结果发到你选的会话 |
| 攒一批，让 AI 汇总 | 一个来源、一个 AI、一个聊天渠道 | 来的内容先攒着 → 每天 9 点把这一批交给 AI 汇总 → 结果发到你选的会话 |
| 规则失败时通知我 | 一个聊天渠道 | 有规则运行失败 → 把是哪条规则、哪个节点、什么错误发到你选的会话 |
| 从空白开始 | 无 | 只有一个触发节点的画布 |

在「记录」里看到一个没有触发任何规则的事件时，点开它可以「用它建一条规则」。

### 导出和导入

规则可以发给别人。在规则编辑器右上角点「导出」，得到一段 JSON，复制或存成 `.cat-rule.json` 文件；对方在「规则」页点「导入」，粘贴或选文件。规则里用到的接入是你这台机器上的，对方那里没有，所以导入时会列出它用到哪些接入（是哪种插件、原来叫什么），让对方从自己的接入里各选一个来顶替，没有的可以当场接入。HTTP 请求、定时触发这类不用接入的不问。选完打开编辑器，看过再保存。

导出的内容里有节点上填的一切：地址、请求头、会话 ID、提示词。接入本身的密钥（机器人令牌等）不在里面。发出去之前看一眼。

## 订阅 RSS / RSSHub

RSS 和 RSSHub 是两个插件。RSS 不用先接入，Cat 自带一个；RSSHub 要连到一个实例，在「接入」页里添加。订阅什么都写在规则里：在规则的触发节点里点 **RSS**（或选「只听指定的」勾上接入的 RSSHub），下面就会出现要填的订阅。

**RSS**：在触发节点的「订阅源」里每行填一个 RSS / Atom 源的完整地址，检查间隔和「首次订阅时把已有条目也当作新条目」也在那里：

```
https://go.dev/blog/feed.atom
```

**RSSHub**：添加时接入向导问用哪个实例。在触发节点的「路由」里每行填一个路由：

```
/github/issue/DIYgod/RSSHub
```

填了订阅的触发节点只接收这些订阅的新条目。几条规则填同一个订阅时只抓取一次；规则停用或删除后，没有别的规则在用的订阅不再抓取。RSSHub 接入的设置里也可以填路由（「始终订阅的…」），它们不管有没有规则用到都会抓取。

| 方式 | 说明 |
| --- | --- |
| 用已有的 RSSHub | 填「RSSHub 地址」，自建实例设置了 `ACCESS_KEY` 时填「访问密钥」。公共实例 `rsshub.app` 经常被限流 |
| 由 Cat 在 Docker 里运行 | Cat 在 Docker 容器里运行 RSSHub 的官方镜像，需要已安装 Docker |
| 由 Cat 用本机的 Node.js 运行 | Cat 下载 RSSHub 源码，用本机的 Node.js 和 pnpm 安装依赖并构建（几分钟，约 1 GB），再用 Node.js 运行；没有 pnpm 时通过 npx 获取 |

由 Cat 运行的 RSSHub 随这个接入启动和停止，只监听本机（`127.0.0.1`），并带一个自动生成的访问密钥；拉取镜像和下载源码之前都会先问你。两种方式都不带浏览器，少数需要浏览器渲染的路由用不了。要订阅多个实例，就添加多个 RSSHub。

两者发出的事件相同：每个新条目是一个 `feed.item` 事件，`payload.text` 是「标题 + 摘要 + 链接」，可以直接转发；另有 `title`、`link`、`content`（纯文本全文）、`content_html`、`author`、`categories`、`images`、`published`。`conversation.id` 是订阅源地址或路由，`conversation.name` 是它的标题，可以用来区分不同的源。

新加入的订阅源和路由只记录现有条目，之后出现的才会触发规则。看过哪些条目是按订阅记的，改规则或重建规则不会把旧条目再发一遍。

## 监控网页变动

网页变动不用先接入，Cat 自带一个。在规则的触发节点里点 **网页变动**，在「网页」里每行填一个地址；只想盯页面上的某一块时，在地址后面空一格写 CSS 选择器：

```
https://example.com/changelog
https://example.com/pricing  #price    # 只看 id 为 price 的元素
```

比较的是页面上看得见的文字，标签、样式和空白的变化不算。文字变了就发出一个 `page.changed` 事件：`payload.text` 是「标题 + 新增和删除的行 + 地址」，可以直接转发；另有 `url`、`title`、`added`、`removed`（数组）、`content`（现在的全文）、`previous`（上一次的全文）。

插件只负责发现变化。要收到通知，新建规则时选「有变化就通知我」，在触发节点里填网页，再在动作节点里选发到哪个会话（可以从最近有消息的会话里选）。

- 填了网页的触发节点只接收这些网页的变动；几条规则填同一个网页时只检查一次，规则停用或删除后不再检查。
- 检查间隔和「忽略的内容」也在触发节点里填，各条规则可以不一样。几条规则盯同一个网页时只抓取一次，间隔按最短的来；忽略的内容不同则各盯各的。
- 第一次看到的网页只记录现状，之后变了才触发。
- 每次打开都不一样的内容（时间、访问量）会造成误报：用选择器缩小范围，或在接入的「忽略的内容」里写正则把它们去掉。
- 只抓取网页源码，不执行 JavaScript；靠脚本渲染的页面抓不到内容，可以用下面的「接口变动」改盯它背后的数据接口。

## 监控接口返回变动

接口变动也不用先接入。在规则的触发节点里点 **接口变动**，在「接口」里每行填一个地址；只想盯返回里的某个字段时，在地址后面空一格写字段路径；不是 GET 请求时把方法写在最前面：

```
https://api.example.com/app/latest
https://api.example.com/app/latest  data.version     # 只看这个字段
POST https://api.example.com/orders/query  data.items  # 请求体填在接入的「请求体」里
```

比较的是解析后的 JSON，字段顺序和空白的变化不算。数据变了就发出一个 `api.changed` 事件：`payload.text` 是「接口 + 变了的字段」，可以直接转发；另有 `changes`（数组，每项有 `path`、`type`（`added` / `removed` / `changed`）、`old`、`new`）、`value`（现在的值）、`previous`（上一次的值）、`url`、`method`、`path`。返回不是 JSON 时整段当作一个字符串比较。

和网页变动一样，插件只负责发现变化，通知靠规则：新建规则时选「有变化就通知我」。填了接口的触发节点只接收这些接口的变动。

- 第一次请求只记录现状，之后变了才触发。
- 每次请求都不一样的字段（时间戳、请求 ID）会造成误报：用字段路径缩小范围，或在「忽略的字段」里把它们去掉，例如 `timestamp`、`items[*].updated_at`。
- 接口报错（状态码不是 2xx），或返回里找不到要盯的字段，算检查失败，不算变动。
- 需要认证的接口把认证信息填在触发节点的「请求头」里，例如 `Authorization: Bearer xxxxxx`；请求体、检查间隔和「忽略的字段」也在那里。它们对这个触发节点里的所有接口生效，认证不同的接口分到两个触发节点。请求头随规则一起保存在本机的数据库里。
- 列表里插入或删除一项时，只报告多出来或少掉的那一项，不会把后面的每一项都算作变了。

## 定时触发

定时触发不用先接入，Cat 自带一个。在规则的触发节点里点 **定时触发**，在「什么时候」里每行写一个：先写时间，空一格后面可以跟一段内容。

```
9:00  汇总昨天的 GitHub 通知，列出需要我处理的     # 每天 9 点
0 18 * * 5  该写周报了                             # cron：分 时 日 月 周，这是每周五 18 点
@every 30m                                         # 每 30 分钟，落在每小时的 0 分和 30 分
```

到点就发出一个 `schedule.fired` 事件：`payload.text` 是时间后面的那段内容，另有 `schedule`（时间的写法）、`scheduled`（应当触发的时刻）、`date`、`time`、`weekday`、`missed`、`manual`。`conversation.id` 是这一整行。填了时间的触发节点只在这些时间触发；几条规则填同一个时间时只发一个事件。

它和 AI、渠道直接组合。比如每天让 AI 汇总再发到群里，新建规则时选「定时让 AI 干活」，生成的就是下面这条规则：

1. 触发节点选定时触发，「什么时候」里填时间和要 AI 做的事。
2. 后面接一个动作，选 AI，操作是「对话」，提示词保持 `{{ payload.text }}`（也可以直接把提示词写在这里，用 `{{ payload.date }}` 带上日期）。
3. 再接一个动作，选聊天渠道，操作选「发送到指定会话」，内容用「插入变量」选上一步 AI 的 `text`。

只是定时提醒的话不需要 AI：触发后面直接接「发送到指定会话」，内容填 `{{ payload.text }}`。

- 时间按这台机器的时区算，也可以在触发节点的「时区」里指定，如 `Asia/Shanghai`。
- 到点时电脑在睡眠或 Cat 没在运行，这一次默认跳过。在触发节点里打开「错过的补发一次」后会在恢复时补发，同一个定时不管错过几次都只补一次，事件里 `missed` 为 `true`。
- 「立即触发」是这个插件提供的动作：放进另一条规则里（比如由 Webhook 或聊天里的一句口令触发），不等到点就发出定时事件，用来试规则或手动补跑。
- AI 默认按 `conversation.id` 续接对话，所以同一个定时每次触发都接着上一次聊。想每次从头开始，勾上 AI 节点的「丢弃之前的对话，重新开始」。

## 攒一批再处理

默认一个事件触发一次运行。想把一段时间里的内容合成一条来处理（把今天的 RSS 和 GitHub 通知汇总成一份、群里连着发的几句话一起交给 AI），在流程里加一个动作，选 **攒一批**：

| 参数 | 说明 |
| --- | --- |
| 收集什么 | 每个事件收下的那一条，默认 `{{ payload.text }}` |
| 攒够几条就发出 | 到这个条数就把这一批交给后面的节点 |
| 每天几点发出 | 如 `9:00`，多个用逗号分隔；到点时一条都没有就不发 |
| 每隔多少分钟发出 | 从这一批的第一条算起 |
| 分开攒 | 可选。填 `{{ conversation.id }}` 就是每个会话各攒一批 |

「攒够几条」「每天几点」「每隔多久」至少填一个，填了几个就以先到的为准。

事件走到这个节点时，内容被收下，这次运行就停在这里（记录里写着「已收下，现在攒了几条」），不算失败。等这一批发出时，它后面的节点作为一次新的运行执行一次，用 `{{ steps.<节点标识>.text }}`（各条之间空一行）、`.items`（数组）和 `.count` 拿到这一批。正好凑够条数的那个事件不停，直接带着这一批往下走。

攒下的内容存在本机，Cat 重启不会丢；关着的时候过了点，启动后马上补发。规则停用期间到点的那一批留着，等规则启用后发出；规则或这个节点删掉了，它攒的东西也随之丢弃。一批最多 500 条，满了就发出。

## 规则怎么写

一条规则是一张图，在画布上把节点连起来。节点有三种：

| 节点 | 作用 |
|---|---|
| 触发 | 哪些接入的哪些事件会启动规则：「所有接入」或只听指定的，「任何事件」或只在指定的事发生时。一条规则可以有多个触发，各走各的流程 |
| 条件 | 判断事件。成立走「是」那一头，不成立走「否」那一头；也可以不止是与否，而是几个选项里的一个，每个选项一个出口。可以按字段比，也可以交给大模型判断。后面可以接动作，也可以再接条件 |
| 动作 | 做一件事：交给 AI、发消息、发 HTTP 请求、跑脚本。添加时直接选用什么来执行，没接入的可以当场接入 |

一个节点可以连到多个节点。两条线汇到同一个节点时，它只执行一次；某个动作失败只中断它自己那条线，别的线照常执行。

连线可以绕回前面的节点，形成循环：比如让 AI 写一稿，条件不满意就绕回去重写。绕回去的路上必须有一个条件节点，由它决定何时不再循环。每绕回一次，从那个节点起后面的流程重新走一遍，`steps.<id>` 里是各节点最近一次的输出，`loop` 是已经绕回的次数（可以用 `loop >= 3` 限制重试次数）。一次运行最多绕回 100 次，超过就停下并记为失败。

从节点右侧的圆点拖到另一个节点上就是连线，点一下圆点是添加下一步，右键有更多操作。撤销、复制粘贴、删除用常见的快捷键。

**条件**在界面里一行一行地选：哪个字段（内容、发送者、会话……）、怎么比、和什么比。字段不在列表里时选「其他字段…」直接写。也可以切到「表达式」，写 [expr](https://expr-lang.org) 表达式：

```
payload.mentioned == true and actor.id in ["123", "456"]
```

可用变量：`payload`、`actor`、`conversation`、`type`、`source`、`raw`，以及前面动作的输出 `steps.<节点标识>`。

说不清规则、得读懂内容才能判断的（「这是在报故障吗」「这条消息属于哪一类」），切到「模型判断」：选一个接入的模型（「大模型对话」「Magpie」或专做判断的「Jev」），写清楚要判断什么，模型只回答是或否。事件走到这个节点才会去问，每次问一回；判断不出来算出错，这条线到此为止。

条件的「结果」可以从「是 / 否」改成「多个选项」：列出几个选项，节点右边每个选项有一个出口，另有一个「其他」。交给模型时，它从这些选项里选一个；写表达式时，表达式算出来的值和哪个选项一样就走哪个（如 `payload.level` 配选项 `high`、`low`）。模型选了什么，后面的节点用 `{{ steps.<节点标识>.choice }}` 引用。

用 Jev 判断时，结果还带着概率：是否判断给出 `probability`（「是」的概率，默认不低于 0.5 算是，可以调），选项判断给出 `confidence`。想让没把握的走另一条线，在后面接一个表达式条件，如 `steps.c1.confidence > 0.8`。

**动作的参数**里用「插入变量」放进事件的内容和前面动作的结果，它们在输入框里显示成标签（如「内容」「Claude Desktop 的输出」）。存下来的是 `{{ }}` 写法：`{{ payload.text }}` 是事件内容，`{{ steps.s1.text }}` 是标识为 `s1` 的动作节点的输出，也可以直接这样写；节点标识在动作面板的「高级」里。发到哪个会话、允许谁来触发这类参数，可以点「从最近的里选」，不用自己找 ID。

**失败了怎么办**：动作面板的「高级」里可以填「失败后再试几次」。第一次重试前等 5 秒（可以改），之后每次加倍，最长等 5 分钟；记录里会写明试了几次。重试完还是失败，这次运行记为失败，同时 Cat 自己发出一个 `run.failed` 事件：`payload.text` 是「哪条规则、哪个节点、什么错误」，可以直接转发，另有 `rule_id`、`rule_name`、`run_id`、`event_id`、`step`、`error` 和 `errors`（每个失败的节点一项）。新建规则时选「规则失败时通知我」，或者自己在触发节点里把来源选成 **Cat**，就能在失败时收到通知。Cat 自己的事件只给点名要它的触发节点：听「所有接入」的规则不会被它触发；由它触发的规则自己失败了，也不会再发一次。试运行和重放的失败不发。

Cat 在一次运行跑完之前退出了（崩溃、被强行结束、断电），下次启动时这次运行会记为「被打断」，同样发出一个 `run.failed` 事件（`payload.interrupted` 为 `true`）。已经开始的动作可能已经做了，所以不会自动重跑；要补跑，在「记录」里重放那个事件。启动时还在准备中的接入，动作会等它最多 30 秒。

**试运行**：工具栏的「试运行」拿一个收到过的事件，把规则现在的样子跑一遍，不用先保存。动作会真的执行。跑过之后，「插入变量」里能选到每个动作实际给出的值。

以前的规则（一个条件加一串顺序步骤）不用改，照常运行；在编辑器里打开时会显示成等价的一条链。

## 让 AI 用 Cat（MCP）

规则里的 AI 是 Cat 把事件交给它。反过来，也可以让 AI 应用里的 AI 主动用 Cat：Cat 自带一个 [MCP](https://modelcontextprotocol.io) 服务，装进 AI 应用后，那里的 AI 能往渠道发消息、查收到的事件、新建和修改规则。在 Claude Desktop 里说一句「每天 9 点把这几个 RSS 汇总发到群里」，它会自己把规则建好。

到「接入」页最下面的「让 AI 用 Cat」，在找到的应用后面点「安装」，重开那个应用后生效；「卸载」把它拿掉。

| 应用 | 装到哪里 |
| --- | --- |
| Claude Desktop | `claude` 命令的用户级 MCP 服务（`claude mcp add --scope user`），Claude Desktop 的 Code 和 Claude Code 共用 |
| ChatGPT Desktop | `~/.codex/config.toml` 里的 `[mcp_servers.cat]`，ChatGPT Desktop 的 Codex 和 `codex` 命令共用 |
| DeepSeek Harness | 每个档案的 `cordis.patch.yml` 里加一个 `cat-mcp` 条目 |

Cat 只增删它自己的那一项，别的配置不动。别的支持 MCP 的应用，把页面上给的地址（`http://127.0.0.1:7788/api/mcp`，Streamable HTTP）填进去就行；Cat 设了 `--token` 时地址里带着令牌。Cat 换了端口或令牌后，页面会提示「装的是另一个地址」，点「重新安装」。

| 工具 | 作用 |
| --- | --- |
| `list_connections` | 有哪些接入，各自能做什么动作、要什么参数 |
| `invoke_action` | 让一个接入做一个动作，比如往某个会话发消息 |
| `list_events`、`get_event` | 最近收到的事件 |
| `list_rules`、`save_rule`、`set_rule_enabled`、`delete_rule` | 查看、新建、修改、启停、删除规则 |
| `try_rule`、`replay_event` | 拿历史事件试运行草稿或已有规则、重放历史事件 |
| `list_runs` | 规则的运行记录，每一步的参数、输出和错误 |

## 安全

- **聊天消息会原样成为给 AI 的指令。** 所以 AI 插件默认只读。Cat 不限制谁发的消息能触发规则：任何能给你的机器人发消息的人都能驱动规则里的 AI，放宽它的权限之前请想清楚谁能给机器人发消息，需要时在规则里用条件节点按发送者筛选。
- **装了 MCP 的 AI 能做你在 Cat 里能做的一切**，包括用「运行脚本」执行命令、建一条以后一直生效的规则。规则里由聊天消息触发的 AI 默认只允许 `Read,Glob,Grep`，用不了这些工具；除非你确实想让聊天里的人通过 AI 操作 Cat，不要把 `mcp__cat__*` 加进它「允许的工具」。
- **插件没有沙箱**，以你的用户身份运行。只安装你信任的插件。从市场安装时会校验 SHA-256。
- 默认只监听本机。要对外提供服务必须设置 `--token`；Webhook 请配置密钥。
- 密钥类配置存放在系统钥匙串（桌面版）或 `~/.cat/secrets.json`（无界面版，仅靠文件权限保护，未加密）。

## 开发

```bash
make test                                # 全部测试
make dev                                 # 热重载：打开桌面窗口，界面改动即时生效，Go / 插件改动后自动重新构建并重启
make dev-web                             # 同上，但用无窗口的 catd，在浏览器打开 http://127.0.0.1:7788
```

调邮件插件不必用真邮箱：`go run ./plugins/internal/mailtest/cmd/mailtest` 在本机起一个只有一个邮箱的邮件服务器（IMAP 1143、SMTP 1025，都不加密），接入时填它的地址并勾上「不加密连接」，发给它 SMTP 的信都进这个邮箱。

### 发布

推送和 PR 会跑 CI（`.github/workflows/ci.yml`）。推一个 `v` 开头的标签就会发布：

```bash
git tag v0.2.0 && git push origin v0.2.0
```

发布流程（`.github/workflows/release.yml`）先跑一遍 CI，再把这些放进 GitHub Release：

- `cat-<版本>-<系统>-<架构>.tar.gz`（Windows 是 `.zip`）：`catd` 和全部官方插件，解压即可运行；`SHA256SUMS` 是它们的校验和。
- 桌面应用，都没有代码签名：
  - `Cat-<版本>-macos-arm64.zip`：首次打开需要在「系统设置 → 隐私与安全性」里放行。
  - `Cat-<版本>-linux-<架构>.tar.gz`（免安装目录）和 `.deb`（装到 `/opt/cat`，依赖 GTK 4 与 WebKitGTK 6.0），有 amd64 和 arm64。
  - `Cat-<版本>-windows-amd64.zip`：免安装目录，首次运行时 SmartScreen 可能提示，选「仍要运行」。
- `update.json`：这一版的版本号，和每种安装包在每个平台上的下载地址与 SHA-256。运行中的 Cat 靠它更新自己（见下面的「自动更新」）。
- 插件市场：每个插件每个平台一个 zip，加上 `index.json`。把 `--market` 指向 `https://github.com/<用户>/<仓库>/releases/latest/download/index.json` 就能一直用最新一版的市场。

在 Actions 页面手动运行 Release 只构建、不发布，产物留在这次运行的附件里，可以用来试跑。本地也能打同样的包：

```bash
make frontend
python3 scripts/build-market.py <基础地址>   # 输出到 dist/market
python3 scripts/build-release.py v0.2.0      # 输出到 dist/release
python3 scripts/build-update.py v0.2.0 <基础地址> dist/release   # 在 dist/release 里写出 update.json
```

### 自动更新

发布出来的 Cat（桌面应用和 `catd`）会自己更新：启动后不久、之后每 6 小时读一次最新 Release 里的 `update.json`，有新版本就在后台下载、校验 SHA-256 并解压。下载好以后界面右上角出现「更新到 x.y.z」，点了才安装：把新文件换到安装位置，然后重新启动（`catd` 原地换成新程序，进程号不变；桌面应用退出后重新打开）。不点就一直用现在的版本。

- 界面左上角的版本号可以点，立即检查一次；桌面应用的托盘菜单里也有「检查更新」。
- 只替换安装包里有的文件，装在旁边的其它插件和文件不动。
- 装的位置改不了（比如 `.deb` 装到 `/opt/cat`）或这个平台没有安装包时，只提示有新版本并给出下载页，需要手动安装。
- `--update <地址>`（或环境变量 `CAT_UPDATE`）换一个 `update.json` 的地址，`--update off` 关掉自动更新。
- 版本号在构建时写进程序（`CAT_VERSION=0.2.0 make app`）；没有版本号的构建（`make run`、`make run-web`、`make dev`、`make dev-web`）是 `dev`，从不更新自己。
- 和插件市场一样，安装包没有代码签名，可信度来自 HTTPS 和 `update.json` 里的校验值。
