# Cat 事件中心

把各处来的事件接到一起，按规则判断，再触发动作。

```
QQ / Discord / Telegram / 企业微信 / RSS / 网页变动 / 接口变动 / 定时 / Webhook ──▶ 规则（条件、分支、节流）──▶ 动作
                                                                                       ├─ 交给 Agent（Claude Code / Codex / DeepSeek）
                                                                                       ├─ 原路回复、跨平台转发
                                                                                       └─ 发 HTTP 请求、跑脚本
```

- **插件化**：每个平台、每种 Agent 都是独立进程的插件，用任何语言都能写。官方提供 Go 和 TypeScript SDK。
- **一键接入**：接入向导负责校验密钥、显示登录二维码、下载并配置依赖，配置表单由插件声明、界面自动生成。
- **从用途开始**：新建规则先选要做的事（聊天机器人、有变化就通知、定时让 Agent 干活……），缺什么当场接入，规则自动搭好。
- **可调试**：规则不用保存就能拿收到过的事件试运行；收到的每个事件、规则对它做的每一步都有记录，历史事件可以重放。
- **两种形态**：桌面应用（托盘常驻）和无界面服务，共用同一个引擎和界面。

## 运行

需要 Go 1.24+、Node + pnpm（构建界面）、Bun（构建 TypeScript 插件）。

```bash
make run                                 # 构建界面、插件、bin/catd 并启动，然后打开 http://127.0.0.1:7788
```

桌面应用（macOS / Linux / Windows，在哪个系统上构建就打哪个系统的包，插件已打包在内）：

```bash
make app
```

| 系统 | 产物 | 构建前需要 |
| --- | --- | --- |
| macOS | `bin/Cat.app` | Xcode 命令行工具 |
| Linux | `bin/Cat-linux/`，有 `dpkg-deb` 时还有 `bin/cat_<版本>_<架构>.deb` | `libgtk-4-dev`、`libwebkitgtk-6.0-dev`（Ubuntu 24.04+ / Debian 13+） |
| Windows | `bin/Cat-windows/` | 在 Git Bash 里运行 `make`；运行时需要 WebView2（Windows 10/11 一般已自带） |

`Cat-linux` 和 `Cat-windows` 是免安装目录，放到哪里都能直接运行；Linux 下执行目录里的 `install.sh` 可以把 Cat 加进应用菜单。

`catd` 的主要参数：

| 参数 | 环境变量 | 说明 |
|---|---|---|
| `--addr` | `CAT_ADDR` | 监听地址，默认 `127.0.0.1:7788` |
| `--data` | `CAT_DATA` | 数据目录，默认 `~/.cat` |
| `--token` | `CAT_TOKEN` | 访问令牌。监听非本机地址时必须设置 |
| `--plugins` | `CAT_PLUGINS` | 额外的插件目录 |
| `--market` | `CAT_MARKET` | 插件市场索引地址 |

运行日志除了打到终端，也写进数据目录下的 `logs/cat.log`（默认 `~/.cat/logs/cat.log`），桌面版同样如此；插件输出的日志也在里面。文件超过 10 MB 会改名为 `cat.log.1` 并另起新文件，最多保留 3 个旧文件。程序崩溃（panic）时的堆栈写在同一目录的 `crash.log`；下次启动会把它改名为 `crash-<崩溃时间>.log` 留档，并在 `cat.log` 里提示一行。

## 第一条规则

界面只有三页：「规则」（什么时候、满足什么条件、做什么）、「接入」（把聊天软件、要盯的东西和 Agent 接进来）、「记录」（收到了什么，规则对它做了什么）。

第一次打开时，「规则」页会问你想做什么。选一个，比如「收到 Webhook 就做点什么」：

1. 它会列出需要的东西。还没有 Webhook 就点「现在接入」，接好后点「下一步」，打开的画布上规则已经搭好：一个触发节点连着一个「HTTP 请求」动作。
2. 点动作节点，填上地址。请求体里可以用「插入变量」放进事件的内容，它在输入框里显示成一个标签。
3. 到「接入」页复制这个 Webhook 的地址，发一个请求：

   ```bash
   curl -X POST http://127.0.0.1:7788/ingress/<Webhook 地址里的那一段> -d '{"text":"please deploy"}'
   ```

4. 回到规则，点「试运行」：拿刚收到的事件把规则跑一遍，每个动作节点上会标出成功还是失败，点进去看结果。满意了再保存。
5. 之后每次请求的结果都在「记录」里。

其他几个起点：

| 起点 | 需要接入 | 生成的规则 |
| --- | --- | --- |
| 聊天机器人 | 一个聊天渠道、一个 Agent | 有人 @ 机器人 → 交给 Agent → 答案发回原处 |
| 有变化就通知我 | 一个监控（RSS、网页变动、接口变动）、一个聊天渠道 | 有变化 → 把内容发到你选的会话 |
| 定时让 Agent 干活 | 定时触发、一个 Agent、一个聊天渠道 | 到点 → 交给 Agent → 结果发到你选的会话 |
| 从空白开始 | 无 | 只有一个触发节点的画布 |

在「记录」里看到一个没有触发任何规则的事件时，点开它可以「用它建一条规则」。

## 订阅 RSS / RSSHub

RSS 和 RSSHub 是两个插件，都在「接入」→「监控」里。

**RSS**：在「订阅源」里每行填一个 RSS / Atom 源的完整地址：

```
https://go.dev/blog/feed.atom
```

**RSSHub**：添加时接入向导先问用哪个实例，再问要订阅的路由，每行一个：

```
/github/issue/DIYgod/RSSHub
```

| 方式 | 说明 |
| --- | --- |
| 用已有的 RSSHub | 填「RSSHub 地址」，自建实例设置了 `ACCESS_KEY` 时填「访问密钥」。公共实例 `rsshub.app` 经常被限流 |
| 由 Cat 在 Docker 里运行 | Cat 在 Docker 容器里运行 RSSHub 的官方镜像，需要已安装 Docker |
| 由 Cat 用本机的 Node.js 运行 | Cat 下载 RSSHub 源码，用本机的 Node.js 和 pnpm 安装依赖并构建（几分钟，约 1 GB），再用 Node.js 运行；没有 pnpm 时通过 npx 获取 |

由 Cat 运行的 RSSHub 随这个接入启动和停止，只监听本机（`127.0.0.1`），并带一个自动生成的访问密钥；拉取镜像和下载源码之前都会先问你。两种方式都不带浏览器，少数需要浏览器渲染的路由用不了。要订阅多个实例，就添加多个 RSSHub。

两者发出的事件相同：每个新条目是一个 `feed.item` 事件，`payload.text` 是「标题 + 摘要 + 链接」，可以直接转发；另有 `title`、`link`、`content`（纯文本全文）、`content_html`、`author`、`categories`、`images`、`published`。`conversation.id` 是订阅源地址或路由，`conversation.name` 是它的标题，可以用来区分不同的源。

新加入的订阅源和路由只记录现有条目，之后出现的才会触发规则。

## 监控网页变动

「接入」→「监控」→ 添加 **网页变动**，在「网页」里每行填一个地址；只想盯页面上的某一块时，在地址后面空一格写 CSS 选择器：

```
https://example.com/changelog
https://example.com/pricing  #price    # 只看 id 为 price 的元素
```

比较的是页面上看得见的文字，标签、样式和空白的变化不算。文字变了就发出一个 `page.changed` 事件：`payload.text` 是「标题 + 新增和删除的行 + 地址」，可以直接转发；另有 `url`、`title`、`added`、`removed`（数组）、`content`（现在的全文）、`previous`（上一次的全文）。

插件只负责发现变化。要收到通知，新建规则时选「有变化就通知我」，再在动作节点里选发到哪个会话（可以从最近有消息的会话里选）。

- 第一次看到的网页只记录现状，之后变了才触发。
- 每次打开都不一样的内容（时间、访问量）会造成误报：用选择器缩小范围，或在「忽略的内容」里写正则把它们去掉。
- 只抓取网页源码，不执行 JavaScript；靠脚本渲染的页面抓不到内容，可以用下面的「接口变动」改盯它背后的数据接口。

## 监控接口返回变动

「接入」→「监控」→ 添加 **接口变动**，在「接口」里每行填一个地址；只想盯返回里的某个字段时，在地址后面空一格写字段路径；不是 GET 请求时把方法写在最前面：

```
https://api.example.com/app/latest
https://api.example.com/app/latest  data.version     # 只看这个字段
POST https://api.example.com/orders/query  data.items  # 请求体填在「请求体」里
```

比较的是解析后的 JSON，字段顺序和空白的变化不算。数据变了就发出一个 `api.changed` 事件：`payload.text` 是「接口 + 变了的字段」，可以直接转发；另有 `changes`（数组，每项有 `path`、`type`（`added` / `removed` / `changed`）、`old`、`new`）、`value`（现在的值）、`previous`（上一次的值）、`url`、`method`、`path`。返回不是 JSON 时整段当作一个字符串比较。

和网页变动一样，插件只负责发现变化，通知靠规则：新建规则时选「有变化就通知我」。

- 第一次请求只记录现状，之后变了才触发。
- 每次请求都不一样的字段（时间戳、请求 ID）会造成误报：用字段路径缩小范围，或在「忽略的字段」里把它们去掉，例如 `timestamp`、`items[*].updated_at`。
- 接口报错（状态码不是 2xx），或返回里找不到要盯的字段，算检查失败，不算变动。
- 认证信息填在「Authorization」里，会按密钥保存；其他请求头填在「请求头」。它们对同一个监控里的所有接口生效，认证不同的接口另建一个监控。
- 列表里插入或删除一项时，只报告多出来或少掉的那一项，不会把后面的每一项都算作变了。

## 定时触发

「接入」→「监控」→ 添加 **定时触发**，在「定时」里每行写一个：先写时间，空一格后面可以跟一段内容。

```
9:00  汇总昨天的 GitHub 通知，列出需要我处理的     # 每天 9 点
0 18 * * 5  该写周报了                             # cron：分 时 日 月 周，这是每周五 18 点
@every 30m                                         # 每 30 分钟，落在每小时的 0 分和 30 分
```

到点就发出一个 `schedule.fired` 事件：`payload.text` 是时间后面的那段内容，另有 `schedule`（时间的写法）、`scheduled`（应当触发的时刻）、`date`、`time`、`weekday`、`missed`、`manual`。`conversation.id` 是这一整行，同一个接入里有多个定时时用它区分。

它和 Agent、渠道直接组合。比如每天让 Agent 汇总再发到群里，新建规则时选「定时让 Agent 干活」，生成的就是下面这条规则：

1. 触发节点只听这个定时。
2. 后面接一个动作，选 Agent，操作是「对话」，提示词保持 `{{ payload.text }}`（也可以直接把提示词写在这里，用 `{{ payload.date }}` 带上日期）。
3. 再接一个动作，选聊天渠道，操作选「发送到指定会话」，内容用「插入变量」选上一步 Agent 的 `text`。

只是定时提醒的话不需要 Agent：触发后面直接接「发送到指定会话」，内容填 `{{ payload.text }}`。

- 时间按这台机器的时区算，也可以在「时区」里指定，如 `Asia/Shanghai`。
- 到点时电脑在睡眠或 Cat 没在运行，这一次默认跳过。打开「错过的补发一次」后会在恢复时补发，同一个定时不管错过几次都只补一次，事件里 `missed` 为 `true`。
- 「立即触发」是这个插件提供的动作：放进另一条规则里（比如由 Webhook 或聊天里的一句口令触发），不等到点就发出定时事件，用来试规则或手动补跑。
- Agent 默认按 `conversation.id` 续接对话，所以同一个定时每次触发都接着上一次聊。想每次从头开始，勾上 Agent 节点的「丢弃之前的对话，重新开始」。

## 规则怎么写

一条规则是一张图，在画布上把节点连起来。常用的节点有三种：

| 节点 | 作用 |
|---|---|
| 触发 | 哪些接入的哪些事件会启动规则：「所有接入」或只听指定的，「任何事件」或只在指定的事发生时。还可以限制频率：一段时间内只触发一次，可以按发送者或会话分别计算。一条规则可以有多个触发，各走各的流程 |
| 条件 | 判断事件。成立走「是」那一头，不成立走「否」那一头；也可以不止是与否，而是几个选项里的一个，每个选项一个出口。可以按字段比，也可以交给大模型判断。后面可以接动作，也可以再接条件 |
| 动作 | 做一件事：交给 Agent、发消息、发 HTTP 请求、跑脚本。添加时直接选用什么来执行，没接入的可以当场接入 |

一个节点可以连到多个节点。两条线汇到同一个节点时，它只执行一次；某个动作失败只中断它自己那条线，别的线照常执行。连线不能绕回前面形成循环。

从节点右侧的圆点拖到另一个节点上就是连线，点一下圆点是添加下一步，右键有更多操作。撤销、复制粘贴、删除用常见的快捷键。

只想限制某一条分支的频率时，在画布空白处或连线上右键，添加一个单独的「节流」节点：事件走到它那里，一段时间内只放行一次。

**条件**在界面里一行一行地选：哪个字段（内容、发送者、会话……）、怎么比、和什么比。字段不在列表里时选「其他字段…」直接写。也可以切到「表达式」，写 [expr](https://expr-lang.org) 表达式：

```
payload.mentioned == true and actor.id in ["123", "456"]
```

可用变量：`payload`、`actor`、`conversation`、`type`、`source`、`raw`，以及前面动作的输出 `steps.<节点标识>`。

说不清规则、得读懂内容才能判断的（「这是在报故障吗」「这条消息属于哪一类」），切到「模型判断」：选一个接入的模型（「大模型对话」「Magpie」或专做判断的「Jev」），写清楚要判断什么，模型只回答是或否。事件走到这个节点才会去问，每次问一回；判断不出来算出错，这条线到此为止。

条件的「结果」可以从「是 / 否」改成「多个选项」：列出几个选项，节点右边每个选项有一个出口，另有一个「其他」。交给模型时，它从这些选项里选一个；写表达式时，表达式算出来的值和哪个选项一样就走哪个（如 `payload.level` 配选项 `high`、`low`）。模型选了什么，后面的节点用 `{{ steps.<节点标识>.choice }}` 引用。

用 Jev 判断时，结果还带着概率：是否判断给出 `probability`（「是」的概率，默认不低于 0.5 算是，可以调），选项判断给出 `confidence`。想让没把握的走另一条线，在后面接一个表达式条件，如 `steps.c1.confidence > 0.8`。

**动作的参数**里用「插入变量」放进事件的内容和前面动作的结果，它们在输入框里显示成标签（如「内容」「Claude Code 的输出」）。存下来的是 `{{ }}` 写法：`{{ payload.text }}` 是事件内容，`{{ steps.s1.text }}` 是标识为 `s1` 的动作节点的输出，也可以直接这样写；节点标识在动作面板的「高级」里。发到哪个会话、允许谁来触发这类参数，可以点「从最近的里选」，不用自己找 ID。

**试运行**：工具栏的「试运行」拿一个收到过的事件，把规则现在的样子跑一遍，不用先保存。动作会真的执行。跑过之后，「插入变量」里能选到每个动作实际给出的值。

以前的规则（一个条件加一串顺序步骤）不用改，照常运行；在编辑器里打开时会显示成等价的一条链。

| Jev | [TypeSafe](https://typesafe.ai) 的 System One 模型：不生成文字，只做判断，快而便宜。专门给条件节点用，还给出判断的概率 |

## 安全

- **聊天消息会原样成为给 Agent 的指令。** 所以 Agent 插件默认只读、只接受白名单里的发送者。有人被拒绝时，在「记录」里点开那一条，可以直接「允许」这个人。放宽之前请想清楚谁能给你的机器人发消息。
- **插件没有沙箱**，以你的用户身份运行。只安装你信任的插件。从市场安装时会校验 SHA-256。
- 默认只监听本机。要对外提供服务必须设置 `--token`；Webhook 请配置密钥。
- 密钥类配置存放在系统钥匙串（桌面版）或 `~/.cat/secrets.json`（无界面版，仅靠文件权限保护，未加密）。

```bash
make test                                # 全部测试
make dev                                 # 热重载：打开 http://127.0.0.1:7788，界面改动即时生效，Go / 插件改动后自动重新构建并重启后端
```

### 发布

推送和 PR 会跑 CI（`.github/workflows/ci.yml`）。推一个 `v` 开头的标签就会发布：

```bash
git tag v0.2.0 && git push origin v0.2.0
```

发布流程（`.github/workflows/release.yml`）先跑一遍 CI，再把这些放进 GitHub Release：

- `cat-<版本>-<系统>-<架构>.tar.gz`（Windows 是 `.zip`）：`catd` 和全部官方插件，解压即可运行；`SHA256SUMS` 是它们的校验和。
- 桌面应用，都没有代码签名：
  - `Cat-<版本>-macos-arm64.zip`：首次打开需要在「系统设置 → 隐私与安全性」里放行。
  - `Cat-<版本>-linux-<架构>.tar.gz`（免安装目录）和 `.deb`（装到 `/opt/cat`，依赖 GTK 4 与 WebKitGTK 6.0），有 amd64 和 arm64。
  - `Cat-<版本>-windows-amd64.zip`：免安装目录，首次运行时 SmartScreen 可能提示，选「仍要运行」。
- 插件市场：每个插件每个平台一个 zip，加上 `index.json`。把 `--market` 指向 `https://github.com/<用户>/<仓库>/releases/latest/download/index.json` 就能一直用最新一版的市场。

在 Actions 页面手动运行 Release 只构建、不发布，产物留在这次运行的附件里，可以用来试跑。本地也能打同样的包：

```bash
make frontend
python3 scripts/build-market.py <基础地址>   # 输出到 dist/market
python3 scripts/build-release.py v0.2.0      # 输出到 dist/release
```
